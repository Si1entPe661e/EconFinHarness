# Present research results

## When to use

Use when actual estimates, descriptive statistics, experimental contrasts, forecast metrics or model-fit outputs must become readable tables/figures. Choose the estimator in the relevant method skill and the uncertainty in inference-clustering before presentation. Formatting must not silently change either.

## Inputs

The requested claim or comparison; fitted model objects or numeric results; actual estimation/evaluation samples; outcome units and estimand; weights, FE and inference choices; method-specific diagnostics; desired format and destination. Read existing output code before replacing its conventions.

## Procedure

1. Choose the result type and the comparisons the reader needs. Read [result-types.md](result-types.md) for descriptive/balance, regression/IV, event/RD, synthetic-control/bunching, structural/GMM, prediction and asset-pricing outputs. Prefer a clear main result followed by necessary diagnostics and sensitivity.
2. Use the same fitted objects and fitted samples as the analysis. Preserve full numeric precision before formatting. Do not recover estimates from screenshots, rounded printed strings or hand-entered stars when the numeric object exists.
3. Keep the estimand and inference aligned. Coefficients, marginal effects, ATT and CAR are different quantities. Read SE, intervals and p-values from the selected result; a covariance matrix alone does not specify finite-sample reference distributions. Bootstrap, randomization or weak-IV results need their actual tests/sets and clear labels.
4. Label column differences: controls, FE, weights, estimator, sample or treatment definition. Use a common sample only when appropriate to the comparison; otherwise explain N differences. Show actual cluster counts by dimension and appropriate fit statistics.
5. Select precision for meaningful effect magnitudes; keep units consistent. State star cutoffs if stars help, and compute them from the intended p-values. Blank/NA means unavailable, absorbed or unsupported, never a zero estimate. Do not exponentiate SE independently when transforming a nonlinear coefficient.
6. Generate requested formats directly from models/results. [code-examples.md](code-examples.md) contains Stata esttab/estpost/putexcel, R etable/modelsummary, Python summary_col and numeric-result exports. Keep an editable/numeric version when useful; a CSV is numeric data rather than a publication layout.
7. For figures, draw intervals from the chosen inference and state pointwise versus simultaneous coverage. Report reference periods, tail bins, support, RD cutoff/window, prediction evaluation dates or other relevant design details. Avoid truncated axes that conceal important uncertainty.
8. Inspect the finished output for clipping, unreadable labels, missing rows, duplicated append blocks, escaped LaTeX characters, stale model selections and incorrect notes. Compare a headline coefficient, its uncertainty and N to the actual model/result.

## Skill composition

Follow the repository file `harness/skill-composition.md`. Reuse the chosen method, sample, weights, FE and inference. If presentation reveals a different sample or uncertainty, return to the relevant analysis step before regenerating the affected output. Do not fit a new model merely to make export easier.

For implementation and discussion, use `harness/workflows/present-results.md`. Use academic-writing only when prose is requested. [checklist.md](checklist.md) and [table_notes.md](templates/table_notes.md) are optional aids.

## Outputs

Return the requested table/figure files and a short explanation of the comparison and any missing results. No separate administrative report or manifest is required.

## Evidence

This is a task skill. It carries no corpus counts and makes no claim about how often any table or figure convention appears in published replication code. Do not cite this file as evidence that a convention is standard or expected.

Method-specific observed practice, with denominators and explicit unknown counts, is in `harness/paradigms/<method>/observed.md` (for example `harness/paradigms/rdd/observed.md`). Recommendations, where they exist, are separate and live in `harness/paradigms/<method>/recommendations.md`.

Existing method observations and paper-practice notes remain available for consultation.
