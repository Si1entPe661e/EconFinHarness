# Evidence tracking

For consequential or reused claims, retain a source pointer, locator, revision and the basis for the judgment. A short answer can cite its source inline; a long or resumable task can use a small ledger.

- Distinguish `reported` (source says it), `verified` (a named check or review supports it), `inferred` (reasoned from sources), `conflicting` and `open`. Metadata identity, file existence and execution success do not verify a substantive claim.
- Cite a file field/line, table, page, stable URL or check log; state what was actually inspected. Preserve who/what performed verification and its scope. A source's self-description remains a report until tested.
- Attach source/result revisions. When a source, producing task or decision changes, mark dependent claims stale and recheck the affected wording, not the entire project automatically.
- Retain counterevidence and unresolved conflicts. An unavailable source or unrun check remains open; do not turn it into a pass.
- Separate task completion from claim support. A completed report can correctly document an unresolved finding.

Use [contracts](../../orchestration/contracts.md#evidence) for the optional machine record and freshness semantics. Research citation identity still belongs to `literature-verification-efh`; use the relevant domain skill to judge substantive support.
