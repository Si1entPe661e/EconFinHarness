# Project planning

Use the user's existing project system. For a small task, a few steps in the conversation are enough.

- State the outcome, audience, deadline if known, constraints and what counts as done. Distinguish commitments from assumptions; do not invent a deadline or staffing capacity.
- Work backward from deliverables. Identify dependencies, accountable owners, required inputs and acceptance checks. A milestone is an observable outcome, not a vague activity.
- Prioritize work that unblocks others or resolves material uncertainty. Separate the next actionable steps from a speculative backlog. Record risks with a trigger and response where useful.
- Estimate effort/ranges only with a stated basis; distinguish forecast dates from agreed dates. Treat scope or decision changes as revisions and identify affected work.
- Choose serial execution or disjoint parallel tasks from dependencies and capacity. Use `task-orchestration-efh` only when execution needs coordination or persistence.

Deliver a concrete plan in the existing format. For longer work, [project plan guidance](references/plan.md) covers milestones, decisions and handoff fields. Current-state verification belongs to `project-status-efh`.
